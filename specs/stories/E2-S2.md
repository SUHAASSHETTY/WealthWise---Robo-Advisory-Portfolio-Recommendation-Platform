## Description

CUSTOMER-only routes `GET /api/v1/risk-profile/questionnaire`, `POST /api/v1/risk-profile/assessments`, `GET /api/v1/risk-profile` and `GET /api/v1/risk-profile/history`, backed by `risk_profile_service` and `risk_assessment_repository`. The service loads the active risk policy, rejects stale `policy_version_id`s, calls `risk_band_rules.assess`, and inserts the assessment and its audit row in one transaction. It exposes `effective_band(customer_id)` for the recommendation story.

## Acceptance criteria

1. **Questionnaire (AC-01.1).** `GET /api/v1/risk-profile/questionnaire` as alice → `200` with `version_no = 1`, a `policy_version_id`, and 7 questions (orders 1–7: AGE, HORIZON, INCOME_STABILITY, EMERGENCY_FUND, LOSS_REACTION, EXPERIENCE, OBJECTIVE), each with 5 options; no `points`, `bands`, `min_score`, `max_score` or `caps` key appears anywhere in the body. dan (ADVISOR) → `403 FORBIDDEN_ROLE`; no token → `401`.
2. **Submit and cap (AC-01.2, AC-01.4).** `POST /api/v1/risk-profile/assessments` with ANS_16 → `201 {assessment_id, total_score: 16, computed_band: "MODERATE", assigned_band: "MODERATE", applied_caps: [], policy_version_no: 1, created_at}`; with ANS_CAP24 → `201` with `total_score = 24`, `computed_band = "AGGRESSIVE"`, `assigned_band = "MODERATE"`, `applied_caps = ["NO_EMERGENCY_FUND"]`. Each submission inserts exactly one `risk_assessments` row and one `audit_events` row (`action = RISK_ASSESSMENT_SUBMITTED`) in the same transaction.
3. **Determinism through the API (AC-01.5).** Submitting ANS_16 twice returns identical `total_score`, `computed_band`, `assigned_band` and two distinct `assessment_id`s; two rows exist.
4. **Invalid submissions (AC-01.6).** ANS_16 without OBJECTIVE → `422` with `error.code = "ANSWER_MISSING"`; AGE answered `GT_10Y` → `422 OPTION_INVALID`; in both cases the `risk_assessments` and `audit_events` row counts are unchanged.
5. **Effective band and append-only history (AC-01.7).** Before any assessment `GET /api/v1/risk-profile` → `200 {"risk_band": null}`. After ANS_16 then ANS_28, it returns `risk_band = "AGGRESSIVE"`, `source = "ASSESSMENT"`, `source_id` = the second `assessment_id`; `GET /api/v1/risk-profile/history` returns both entries newest first with `type = "ASSESSMENT"` and `policy_version_no = 1`. Both rows still exist, and bob's history is empty (ownership via token).
6. **Stale version and no PII in logs (AC-01.8; NFR-03).** With a PUBLISHED v2 risk policy inserted via the repository fixture, submitting with v1's `policy_version_id` → `409 POLICY_VERSION_STALE` and no row is created. Captured logs for the whole flow contain `assessment_id` / `customer_id` but none of: the username, any option code, any band name, or the score (`tests/architecture/test_no_pii_in_logs.py`).
