## Description

End-to-end acceptance coverage proving that publishing new versions through the admin API affects only new actions. Existing assessments and recommendations keep the version they were created under, while new assessments and recommendations use the newly active version. This story adds acceptance tests and any service fixes needed; it introduces no new routes.

## Acceptance criteria

1. **Recommendation keeps its template (AC-10.5).** alice submits ANS_16 and gets a recommendation under template v1 (50.00/35.00/10.00/5.00). erin creates a template draft, sets MODERATE to 45.00/40.00/10.00/5.00 and publishes it (v2). alice's `GET /api/v1/recommendations/latest` still returns `template_version_no = 1` with 50.00/35.00/10.00/5.00, and the stored row's `template_version_id` is v1's id.
2. **New recommendation uses the new template (AC-10.5).** alice then calls `POST /api/v1/recommendations {}` → `201` with `template_version_no = 2` and 45.00/40.00/10.00/5.00; `latest` now returns it, and `GET /api/v1/recommendations` lists both (v2 first).
3. **Assessment keeps its policy (AC-10.6).** bob submits ANS_20 under v1 → `assigned_band = "MODERATE"`. erin publishes risk policy v2 (MODERATE 12–19, AGGRESSIVE 20–28). bob's `GET /api/v1/risk-profile` still returns `risk_band = "MODERATE"`, and history shows `policy_version_no = 1`.
4. **New assessment uses the new policy (AC-10.6, AC-01.8).** The questionnaire now returns `version_no = 2`. Resubmitting ANS_20 with v1's `policy_version_id` → `409 POLICY_VERSION_STALE`; with v2's id → `201` with `total_score = 20`, `assigned_band = "AGGRESSIVE"`, `policy_version_no = 2`, and `GET /api/v1/risk-profile` returns AGGRESSIVE.
5. **Effective band flows into recommendation (AC-10.6, AC-02.2).** After step 4, bob's `POST /api/v1/recommendations {}` returns `risk_band = "AGGRESSIVE"` and the active template's AGGRESSIVE row (75.00/15.00/7.50/2.50 under template v1).
